## Tutorial 10: Interoperability

The scope of this laboratory covers calling native (unmanaged) code from C#: Platform Invoke (`DllImport` and `LibraryImport`), marshalling of strings, arrays, structs and callbacks, wrapping native resources in `SafeHandle`, as well as unsafe code (pointers, `fixed`, `stackalloc`) and its impact on performance.

In C++, using a C library comes down to including its header and linking against it – the compiler checks every call against the declarations from the header. In C#, the compiler never sees the header: the library is loaded at run time, and every function and struct has to be **declared once again in C#**. Nobody checks whether those declarations match the native code – a wrong type or a missing parameter does not cause a compilation error, but a crash or silently corrupted memory. This tutorial shows how to write such declarations correctly. More details can be found in the lectures [Platform Invoke]({{< ref "/lectures/11.interoperability/pinvoke" >}}) and [Unsafe context]({{< ref "/lectures/11.interoperability/unsafe" >}}).

### Managed and Unmanaged Code

C# code is *managed*: it runs under the control of the runtime, which takes care of memory (the Garbage Collector can move objects at any time), checks array bounds and guarantees type safety. Code written in C or C++ and compiled to machine code is *unmanaged* (native) – memory is managed manually, and nothing protects us from going past the end of a buffer.

Calling a native function from C# with **P/Invoke** (*Platform Invoke*) involves several steps performed by the runtime:

1. On the first call, it loads the library (`LoadLibrary` on Windows, `dlopen` on Linux/macOS) and finds the function by name (`GetProcAddress`/`dlsym`).
2. It converts the arguments to their native representation (**marshalling**) – e.g. a `string` (UTF-16 in .NET) to a `char*` in UTF-8.
3. It *pins* managed objects passed by pointer, because the GC may run while the native code executes, and it must not move memory that native code is using.
4. After the call, it converts the result and output parameters back and releases temporary buffers.

In C++ you would do the same by hand:

```cpp
// C++ (Linux): load a library and call a function from it at run time
void* lib = dlopen("libc.so.6", RTLD_NOW);
auto getpid = reinterpret_cast<int (*)()>(dlsym(lib, "getpid"));
int pid = getpid();
```

### `DllImport` and `LibraryImport`

A native function is declared in C# as a `static` method without a body, marked with an attribute that specifies the library name. There are two variants:

```csharp
using System.Runtime.InteropServices;

internal static partial class OsNative
{
    // Classic P/Invoke: the marshalling stub is generated at run time
    [DllImport("libc", EntryPoint = "getpid")]
    internal static extern int GetPidDllImport();

    // Source-generated P/Invoke: the stub is generated at compile time
    [LibraryImport("libc", EntryPoint = "getpid")]
    internal static partial int GetPid();
}
```

- `[DllImport]` (`static extern`) – the runtime generates the code converting arguments (the *stub*) on the first call. It applies many implicit defaults, e.g. how `string` and `bool` are converted.
- `[LibraryImport]` (`static partial`, .NET 7+) – the stub is generated by a *source generator* during compilation, so it can be viewed and debugged, and it works with trimming and Native AOT. It is the recommended way in new code. It requires `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>` in the project (the generated code uses pointers) and an explicit choice of marshalling for non-trivial types (e.g. `StringMarshalling`, `MarshalAs` for `bool`).
- `EntryPoint` is the name of the function in the library – thanks to it, the C# method can have a name following .NET conventions.

### Finding the Library

The library name is given without the prefix and extension, e.g. `"imgfilter"`. The runtime tries the variants appropriate for the operating system: `imgfilter.dll` on Windows, `libimgfilter.so` on Linux and `libimgfilter.dylib` on macOS. It looks first in the application directory (next to `ImageFilters.dll`), and then lets the operating system search its standard locations. Therefore the simplest approach is to place the native library in the output directory of the application.

The library is loaded only on the first call of one of its functions. If it cannot be found, a `DllNotFoundException` is thrown; if it does not export a function with the given name, an `EntryPointNotFoundException` is thrown. Thanks to this lazy loading, declarations of functions from `kernel32.dll` do not interfere with running the program on Linux, as long as they are not called.

> [!TIP]
> The name `"libc"` is handled specially by the runtime: it is mapped to the C standard library (`libc.so.6` on Linux with glibc, `/usr/lib/libc.dylib` on macOS), so the same declaration works on both systems.

### Marshalling and Type Mapping

Types that have the same representation in memory on both sides are called **blittable** – they are passed without any conversion (pointers to them can be passed directly to native code). These are the numeric types, pointers, and structs and arrays consisting only of them. `string`, `bool` and `char` are **non-blittable** – they require conversion, and therefore copying.

The table below shows how common C types map to C#:

| C | C# | Notes |
|---|---|---|
| `int32_t`, `int` | `int` | |
| `uint32_t`, `DWORD` | `uint` | |
| `int64_t` | `long` | |
| `long` | `CLong` | 32 bits on Windows, 64 bits on 64-bit Linux and macOS |
| `uint8_t`, `unsigned char` | `byte` | |
| `float`, `double` | `float`, `double` | |
| `size_t` | `nuint` | pointer-sized |
| `void*`, `intptr_t`, handles | `nint` | pointer-sized |
| `T*` | `T*`, `ref T`, `out T`, `in T`, `T[]`, `Span<T>` | depending on the purpose of the parameter |
| `const char*` (UTF-8) | `string` + `StringMarshalling.Utf8` | input parameters only, see Stage 2 |
| `const wchar_t*` (Windows) | `string` + `StringMarshalling.Utf16` | `wchar_t` is 4 bytes on Linux/macOS |
| `bool` (C99, C++) | `[MarshalAs(UnmanagedType.U1)] bool` | 1 byte |
| `BOOL` (WinAPI) | `[MarshalAs(UnmanagedType.Bool)] bool` | 4 bytes |
| `struct` | `[StructLayout(LayoutKind.Sequential)] struct` | the same fields in the same order |
| function pointer | `delegate* unmanaged[Cdecl]<...>` | see Stage 5 |

### Stage 1: Calling Operating System Functions

We will start without writing any native code – we will call functions exported by the operating system: get the process identifier and try to open a file. Linux and macOS provide them in the C standard library (`libc`), Windows in `kernel32.dll`.

1. Enable unsafe code in `ImageFilters.csproj` by adding `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>` to the `PropertyGroup`. Without it, every `[LibraryImport]` ends with the error `SYSLIB1062`.
2. Create the file `Interop/OsNative.cs` with an `internal static partial class OsNative` in the `ImageFilters.Interop` namespace. Declare (the `partial` keyword is needed both on the class and on the methods):
   - for Linux/macOS (library `"libc"`): `GetPid()` (function `getpid`) with `[LibraryImport]`, and the same function as `GetPidDllImport()` with `[DllImport]`; `Open(string path, int flags)` (function `open`) and `Close(int fd)` (function `close`); the constant `O_RDONLY = 0`;
   - for Windows (library `"kernel32.dll"`): `GetCurrentProcessId()` returning `uint` (also in the `DllImport` variant, as `GetCurrentProcessIdDllImport()`), `CreateFile` (function `CreateFileW`) returning `nint`, `CloseHandle`; the constants `GENERIC_READ = 0x80000000`, `FILE_SHARE_READ = 1`, `OPEN_EXISTING = 3` and the field `INVALID_HANDLE_VALUE = -1` (of type `nint`).

   File functions report errors through `errno` (Unix) or `GetLastError()` (Windows), so they need `SetLastError = true`. Strings are passed to `open` in UTF-8, and to `CreateFileW` (`W` = *wide*) in UTF-16:

   ```csharp
   // int open(const char* path, int flags, ...) - returns -1 and sets errno on failure
   [LibraryImport("libc", EntryPoint = "open", SetLastError = true, StringMarshalling = StringMarshalling.Utf8)]
   internal static partial int Open(string path, int flags);

   // HANDLE CreateFileW(...) - returns INVALID_HANDLE_VALUE and sets GetLastError() on failure
   [LibraryImport("kernel32.dll", EntryPoint = "CreateFileW", SetLastError = true, StringMarshalling = StringMarshalling.Utf16)]
   internal static partial nint CreateFile(string fileName, uint desiredAccess, uint shareMode,
       nint securityAttributes, uint creationDisposition, uint flagsAndAttributes, nint templateFile);

   // BOOL is a 4-byte int in WinAPI
   [LibraryImport("kernel32.dll", EntryPoint = "CloseHandle", SetLastError = true)]
   [return: MarshalAs(UnmanagedType.Bool)]
   internal static partial bool CloseHandle(nint handle);
   ```

3. In `Program.cs`, add a static local function `ShowProcessInfo()` that prints the process identifier obtained in three ways: `LibraryImport`, `DllImport` and `Environment.ProcessId`. Choose the functions for the current system with `OperatingSystem.IsWindows()`.
4. Add a function `TryOpenFile(string path)` that opens the file for reading (`open` with `O_RDONLY` or `CreateFile` with `GENERIC_READ`, `FILE_SHARE_READ` and `OPEN_EXISTING`), prints the descriptor/handle and closes it. On failure, it should print the error code and its description. Call it for `input.ppm` (exists) and `missing.ppm` (does not exist).

> [!IMPORTANT]
> #### `SetLastError` and Error Codes
>
> Native functions often report the cause of an error through a global (thread-local) variable: `errno` in C or `GetLastError()` in WinAPI. However, the runtime itself calls system functions (e.g. when allocating memory), which may overwrite this value before we get a chance to read it. `SetLastError = true` makes the stub save the error code immediately after the call. We read it with `Marshal.GetLastPInvokeError()` (the older `Marshal.GetLastWin32Error()` returns the same value, also on Unix), and `Marshal.GetPInvokeErrorMessage(code)` converts it into a system message:
>
> ```csharp
> static void PrintLastError(string call)
> {
>     // errno (Unix) or GetLastError() (Windows), saved right after the call thanks to SetLastError = true
>     int error = Marshal.GetLastPInvokeError();
>     Console.WriteLine($"{call} failed: error {error} - {Marshal.GetPInvokeErrorMessage(error)}");
> }
> ```

> [!TIP]
> The code generated by `[LibraryImport]` can be viewed in the IDE (*Dependencies → Analyzers → Microsoft.Interop.LibraryImportGenerator*) or saved to `obj/Debug/net10.0/generated` after adding `<EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles>` to the project. For `Open`, it looks as follows (shortened) – the string is converted to UTF-8 into a buffer on the stack, `errno` is saved right after the call, and the actual import has only blittable parameters:
>
> ```csharp
> internal static partial int Open(string path, int flags)
> {
>     int __lastError;
>     byte* __path_native = default;
>     int __retVal = default;
>     scoped Utf8StringMarshaller.ManagedToUnmanagedIn __path_native__marshaller = new();
>     try
>     {
>         __path_native__marshaller.FromManaged(path, stackalloc byte[Utf8StringMarshaller.ManagedToUnmanagedIn.BufferSize]);
>         {
>             __path_native = __path_native__marshaller.ToUnmanaged();
>             Marshal.SetLastSystemError(0);
>             __retVal = __PInvoke(__path_native, flags);
>             __lastError = Marshal.GetLastSystemError();
>         }
>     }
>     finally
>     {
>         __path_native__marshaller.Free();
>     }
>     Marshal.SetLastPInvokeError(__lastError);
>     return __retVal;
>
>     [DllImport("libc", EntryPoint = "open", ExactSpelling = true)]
>     static extern unsafe int __PInvoke(byte* __path_native, int __flags_native);
> }
> ```

### Stage 2: Your Own Native Library

In this stage, we will write the `imgfilter` library in C, compile it on each operating system and call its first functions.

> [!IMPORTANT]
> #### Exporting Functions from a Shared Library
>
> For a function to be callable from outside a shared library, it has to be **exported** under a known name:
> - The library is written in C, so function names are not mangled. In C++ you have to declare functions with `extern "C"` – otherwise the compiler encodes parameter types in the name (*name mangling*) and P/Invoke will not find the function.
> - MSVC exports only functions marked with `__declspec(dllexport)`. GCC and Clang export all functions by default, but with the `-fvisibility=hidden` flag, they behave like MSVC: only functions marked with `__attribute__((visibility("default")))` are exported.
>
> Both cases are handled by a macro in the header file. The same header can be included by C code using the library – then `IMGFILTER_EXPORTS` is not defined and the macro expands to `__declspec(dllimport)`:
>
> ```c
> #if defined(_WIN32)
> #  if defined(IMGFILTER_EXPORTS)
> #    define IMGF_API __declspec(dllexport)
> #  else
> #    define IMGF_API __declspec(dllimport)
> #  endif
> #else
> #  define IMGF_API __attribute__((visibility("default")))
> #endif
> ```

1. Create the directory `ImageFilters/native` and the header `imgfilter.h` in it with the `IMGF_API` macro above (and the usual include guard and `extern "C"` block for C++ users). Declare:

   ```c
   IMGF_API int32_t imgf_add(int32_t a, int32_t b);
   /* Returns a static string - the caller must NOT free it */
   IMGF_API const char* imgf_version(void);
   /* Returns a newly allocated string - the caller must free it with imgf_free */
   IMGF_API char* imgf_build_info(void);
   IMGF_API void imgf_free(void* ptr);
   ```

2. Create `imgfilter.c`. Start it with `#define IMGFILTER_EXPORTS` placed **before** `#include "imgfilter.h"` – we are building the library itself. Implement:
   - `imgf_add` – returns the sum.
   - `imgf_version` – returns the string literal `"imgfilter 1.0"`.
   - `imgf_build_info` – returns a string allocated with `malloc`, e.g. `"imgfilter 1.0, GCC 15.3.1, 64-bit"`. The compiler can be recognized by its predefined macros (`__clang__` and `__clang_version__`, `_MSC_VER`, `__GNUC__` and `__VERSION__`), the bitness by `sizeof(void*)`. The required buffer length can be obtained by calling `snprintf(NULL, 0, format, ...)`.
   - `imgf_free` – calls `free`.

3. Compile the library manually in the `native` directory to make sure it works:

   ```bash
   # Linux
   cc -std=c11 -O2 -Wall -shared -fPIC -fvisibility=hidden -o libimgfilter.so imgfilter.c
   nm -D --defined-only libimgfilter.so          # list exported functions

   # macOS
   cc -std=c11 -O2 -Wall -shared -fPIC -fvisibility=hidden -o libimgfilter.dylib imgfilter.c
   nm -gU libimgfilter.dylib

   # Windows (x64 Native Tools Command Prompt for VS)
   cl /nologo /O2 /W3 /LD imgfilter.c /Feimgfilter.dll
   dumpbin /exports imgfilter.dll
   ```

   `-shared` (`/LD` for MSVC) creates a shared library instead of an executable, and `-fPIC` generates position-independent code, required in shared libraries on Linux.

4. Building manually after every change and copying the result to `bin/Debug/net10.0` is tedious. Let MSBuild do it – add the following to `ImageFilters.csproj` (you know properties, items and targets from [Tutorial 2]({{< ref "/labs/02.msbuild" >}})):

   ```xml
   <!-- File name of the native library on the current operating system -->
   <PropertyGroup>
     <NativeLibName Condition="$([MSBuild]::IsOSPlatform('Windows'))">imgfilter.dll</NativeLibName>
     <NativeLibName Condition="$([MSBuild]::IsOSPlatform('OSX'))">libimgfilter.dylib</NativeLibName>
     <NativeLibName Condition="'$(NativeLibName)' == ''">libimgfilter.so</NativeLibName>
   </PropertyGroup>

   <ItemGroup>
     <NativeSource Include="native/*.c;native/*.h" />
   </ItemGroup>

   <!-- Compile the C library into the output directory, next to ImageFilters.dll.
        Inputs/Outputs: the target is skipped when the library is up to date. -->
   <Target Name="BuildNative" AfterTargets="Build" Inputs="@(NativeSource)" Outputs="$(OutDir)$(NativeLibName)">
     <Exec Condition="!$([MSBuild]::IsOSPlatform('Windows'))"
           Command="cc -std=c11 -O2 -Wall -shared -fPIC -fvisibility=hidden -o $(OutDir)$(NativeLibName) native/imgfilter.c" />
     <!-- Requires cl.exe on PATH: run dotnet build/run from the "x64 Native Tools Command Prompt for VS" -->
     <Exec Condition="$([MSBuild]::IsOSPlatform('Windows'))"
           Command="cl /nologo /O2 /W3 /LD native\imgfilter.c /Fo$(IntermediateOutputPath) /Fe$(OutDir)$(NativeLibName)" />
   </Target>
   ```

   From now on, `dotnet build` and `dotnet run` (also with `-c Release`) compile the library into the output directory whenever `imgfilter.c` or `imgfilter.h` changes. Remove the files compiled manually in step 3.

> [!WARNING]
> - On Windows, `cl` is available only in the *Native Tools Command Prompt*. A build started from a regular console or from the IDE ends with the error `MSB3073` (exit code 9009 – command not found).
> - The library must have the same architecture as the .NET process (`RuntimeInformation.ProcessArchitecture`). A 32-bit DLL built in the default *Developer Command Prompt* (x86) or an x64 library loaded by an ARM64 process ends with a `BadImageFormatException` or a `DllNotFoundException`.

5. Create the file `Interop/ImgFilterNative.cs` with an `internal static partial class ImgFilterNative` containing the raw declarations (`private const string Lib = "imgfilter";`): `Add`, `Version`, `BuildInfo` and `Free`, using `EntryPoint` to map them to `imgf_add`, `imgf_version` and so on. Native strings are returned as `nint` (see below).
6. Create a public static class `ImgFilter` (`ImgFilter.cs`) – a managed API hiding the raw declarations: `Add(int a, int b)`, and properties `Version` and `BuildInfo` returning `string`.
7. In `Program.cs`, add `ShowLibraryInfo()` printing the version, the result of `ImgFilter.Add(2, 3)` and the build information.

> [!WARNING]
> #### Who Owns the Returned Memory?
>
> A `string` return type looks tempting, but then the marshaller not only copies the native string, it also **frees** it with `Marshal.FreeCoTaskMem` (`free` on Unix, `CoTaskMemFree` on Windows). For `imgf_version`, which returns a string literal, this means freeing memory that was never allocated – the process crashes (on Linux with `free(): invalid size`). Even for `imgf_build_info`, it works only by accident on Linux: memory allocated with `malloc` inside a DLL must not be freed with `CoTaskMemFree`, and on Windows the DLL may even use a different C runtime (a different heap) than the rest of the process.
>
> The rule is therefore: return `nint`, copy the string with `Marshal.PtrToStringUTF8`, and release memory owned by the caller with a function provided by **the same library**:
>
> ```csharp
> // We own the string: copy it and give the memory back to the library
> public static string BuildInfo
> {
>     get
>     {
>         nint ptr = ImgFilterNative.BuildInfo();
>         if (ptr == 0)
>             throw new OutOfMemoryException();
>         try
>         {
>             return Marshal.PtrToStringUTF8(ptr)!;
>         }
>         finally
>         {
>             ImgFilterNative.Free(ptr);
>         }
>     }
> }
> ```

> [!TIP]
> If the library cannot be placed next to the application, or its name differs between systems, you can take over library loading with `NativeLibrary.SetDllImportResolver`. The resolver has to be registered before the first call into the library:
>
> ```csharp
> NativeLibrary.SetDllImportResolver(Assembly.GetExecutingAssembly(), (libraryName, assembly, searchPath) =>
> {
>     if (libraryName != "imgfilter")
>         return 0; // 0 = fall back to the default probing
>     string fileName = OperatingSystem.IsWindows() ? "imgfilter.dll"
>         : OperatingSystem.IsMacOS() ? "libimgfilter.dylib"
>         : "libimgfilter.so";
>     return NativeLibrary.Load(Path.Combine(AppContext.BaseDirectory, "native", fileName));
> });
> ```

2 + 3 =     5

### Stage 3: Arrays and Structs

In this stage, we will implement the first image filters in C: color inversion and conversion to grayscale, as well as computing simple statistics. We will pass the pixel buffer and structs describing the image to the native code.

> [!IMPORTANT]
> #### Blittable Structs
>
> A struct passed to native code must have exactly the same layout in memory as its C counterpart: the same fields, of the same sizes, in the same order. `[StructLayout(LayoutKind.Sequential)]` (the default for C# structs) guarantees that fields are laid out in the order of declaration, with the same alignment rules as in C. In `imgf_stats` below, the compiler inserts 6 bytes of padding after `max` so that `mean` starts at an offset divisible by 8 – the C# struct gets exactly the same padding, and both have 16 bytes (you can check it with `Unsafe.SizeOf<ImageStats>()`). A struct consisting only of blittable fields is blittable itself, so it is passed without copying.
>
> ```c
> typedef struct imgf_info
> {
>     int32_t width;
>     int32_t height;
>     int32_t channels;
> } imgf_info;
>
> typedef struct imgf_stats
> {
>     uint8_t min;
>     uint8_t max;
>     double mean;
> } imgf_stats;
> ```
>
> ```csharp
> [StructLayout(LayoutKind.Sequential)]
> public readonly struct ImageInfo(int width, int height, int channels)
> {
>     public readonly int Width = width;
>     public readonly int Height = height;
>     public readonly int Channels = channels;
> }
> ```

> [!IMPORTANT]
> #### Passing Buffers and References
>
> A C function receiving `T*` can be declared in C# in several ways:
> - `T[]`, `Span<T>` (for `const T*`: `ReadOnlySpan<T>`) – for arrays of blittable types, the stub pins the memory for the duration of the call and passes a pointer to the first element, without copying. Thus native code modifies the C# array directly.
> - `ref T` – a pointer to a variable that native code reads and modifies, `in T` – a pointer to data that native code only reads (`const T*`), `out T` – a pointer to a variable that native code only writes.
> - `T*` – a raw pointer, requires an `unsafe` context.
>
> Native code knows nothing about `Length` – it receives only the address. **The size of the buffer always has to be passed explicitly**, and the native code has to check it. If it writes past the end of the buffer, no `IndexOutOfRangeException` is thrown – memory gets silently corrupted, and the program may crash much later in a completely unrelated place.

1. In `imgfilter.h`, add the structs shown above, error codes (`IMGF_OK = 0`, `IMGF_ERR_NULL_POINTER = -1`, `IMGF_ERR_INVALID_ARGUMENT = -2`, `IMGF_ERR_BUFFER_TOO_SMALL = -3`, `IMGF_ERR_CHANNELS = -4`, `IMGF_ERR_OUT_OF_MEMORY = -5`) and the functions:

   ```c
   /* Returns a static description of an error code */
   IMGF_API const char* imgf_error_message(int32_t code);

   IMGF_API int32_t imgf_invert(uint8_t* pixels, size_t length, const imgf_info* info);
   IMGF_API int32_t imgf_grayscale(uint8_t* pixels, size_t length, const imgf_info* info);
   IMGF_API int32_t imgf_compute_stats(const uint8_t* pixels, size_t length, const imgf_info* info,
                                       imgf_stats* stats);
   ```

2. Implement them in `imgfilter.c`. All filters work in place and return `IMGF_OK` or an error code:
   - First, validate the arguments (a helper `static` function): `NULL` pointers, non-positive dimensions, the number of channels outside `1..4`, and `length` smaller than `width * height * channels`.
   - `imgf_invert` replaces every byte `v` with `255 - v`.
   - `imgf_grayscale` (requires at least 3 channels) computes the luminance of every pixel using integer weights `gray = (77 * R + 150 * G + 29 * B) >> 8` (the weights 0.299, 0.587, 0.114 multiplied by 256) and writes it to all three channels.
   - `imgf_compute_stats` computes the minimum, maximum and mean of all bytes and writes them to `*stats`.
   - `imgf_error_message` returns a string literal for each error code (e.g. `"pixel buffer is too small"`).
3. In C#, create the structs `ImageInfo` and `ImageStats` (`Interop/ImageInfo.cs`, `Interop/ImageStats.cs`) and add a property `public ImageInfo Info => new(Width, Height, Channels);` to `Image`. Declare the new functions in `ImgFilterNative`:

   ```csharp
   [LibraryImport(Lib, EntryPoint = "imgf_invert")]
   internal static partial int Invert(Span<byte> pixels, nuint length, in ImageInfo info);

   [LibraryImport(Lib, EntryPoint = "imgf_compute_stats")]
   internal static partial int ComputeStats(ReadOnlySpan<byte> pixels, nuint length, in ImageInfo info,
       out ImageStats stats);
   ```

4. In `ImgFilter`, add `ErrorMessage(int code)` and the methods `Invert(Image)`, `Grayscale(Image)` and `ComputeStats(Image)`. Convert error codes into exceptions with a helper method `Check(int code)`, which throws an `InvalidOperationException` with the message from `imgf_error_message` when the code is not `0`.
5. In `Program.cs`, add `RunNativeFilters(Image input)`, which prints the statistics of the input image, saves its inverted copy to `inverted.ppm` and its grayscale copy to `grayscale.ppm` (printing their statistics as well), and finally calls `ImgFilterNative.Invert` directly with a 10-byte array and the dimensions of the input image to see that the native code detects a too small buffer.

### Stage 4: Unsafe Code and Performance

Is it worth calling C code to make the program faster? In this stage, we will implement the same filters in C# in three ways, add a 3x3 box blur, and measure the performance of all variants.

> [!IMPORTANT]
> #### Pointers and `fixed`
>
> In an `unsafe` context (an `unsafe` method, class or block), C# allows pointers with the same operators as C++: `*`, `&`, `->`, `[]` and pointer arithmetic. The address of a managed object (e.g. an array) cannot simply be taken, because the GC can move the object at any time. The `fixed` statement *pins* the object for the duration of the block and gives a pointer to its first element. It also works with `Span<T>`:
>
> ```csharp
> // 3. Unsafe code: pointer arithmetic, no bounds checks
> public static unsafe void GrayscaleUnsafe(Span<byte> pixels)
> {
>     fixed (byte* start = pixels)
>     {
>         byte* end = start + pixels.Length - pixels.Length % 3;
>         for (byte* p = start; p < end; p += 3)
>         {
>             // ...
>         }
>     }
> }
> ```

> [!IMPORTANT]
> #### `stackalloc`
>
> `stackalloc` allocates a small buffer on the stack – like an array declared as a local variable in C++. Such memory does not burden the GC and is released automatically when the method returns. Assigned to a `Span<T>`, it does not even require an `unsafe` context. Stack memory never moves, so it can also be passed to native code without pinning. Use it only for small buffers (up to a few kilobytes), because the stack is small (typically 1 MB on Windows, 8 MB on Linux).

1. Create a struct `Rgb24` (`Rgb24.cs`) – one pixel with three `byte` fields: `[StructLayout(LayoutKind.Sequential)] public record struct Rgb24(byte R, byte G, byte B);`.
2. Create a static class `ManagedFilters` (`ManagedFilters.cs`) and implement grayscale conversion (with the same formula as in C) in three ways:
   - `GrayscaleSafe(byte[] pixels)` – a loop over the array with indexing: `pixels[i]`, `pixels[i + 1]`, `pixels[i + 2]`.
   - `GrayscaleSpan(Span<byte> pixels)` – `MemoryMarshal.Cast<byte, Rgb24>(pixels)` reinterprets the bytes as pixels without copying (similar to `reinterpret_cast` in C++), and `foreach (ref Rgb24 p in ...)` iterates over them by reference, allowing modification.
   - `GrayscaleUnsafe(Span<byte> pixels)` – pointer arithmetic inside `fixed` (see the snippet above).
3. Implement a 3x3 convolution in two variants: `Convolve3x3Safe` (indexing of `byte[]`) and `Convolve3x3Unsafe` (pointers to the source and destination pixels and to the kernel, obtained with `fixed`), both with the signature `(Image source, Image destination, ReadOnlySpan<int> kernel, int divisor)`:
   - For every pixel and every channel, compute the sum of the 9 neighbouring values multiplied by the kernel weights (`kernel[0]` for the top-left neighbour, `kernel[4]` for the pixel itself, `kernel[8]` for the bottom-right one).
   - At the image edges, use the nearest pixel inside the image (clamp the neighbour coordinates to `0..Width-1` and `0..Height-1`).
   - The result is `sum / divisor` clamped to `0..255` (`Math.Clamp`).
   - Write both variants in the same way (e.g. compute the offsets of the rows above and below, and of the left and right columns, once per row/pixel), so that the only difference is indexing vs pointers. Before the unsafe variant, validate the arguments (the same image sizes, 9 kernel elements, a non-zero divisor) – there is no safety net below.
4. Add `BoxBlur(Image source, bool useUnsafe)`, which creates the kernel on the stack and returns a new, blurred image:

   ```csharp
   // Small, short-lived buffer: allocated on the stack, not on the GC heap
   Span<int> kernel = stackalloc int[9];
   kernel.Fill(1);
   ```

5. In `Program.cs`, add `RunManagedFilters(Image input)`, which compares the result of each managed grayscale variant with the native one (`a.Pixels.AsSpan().SequenceEqual(b.Pixels)`), compares the two blur variants and saves the blurred image to `blur.ppm`.
6. Create a static class `Benchmark` (`Benchmark.cs`) with a method `Run()`, called at the end of `Program.cs`. On a 1920x1080 test image, measure the average time of: each grayscale variant (20 iterations; repeated conversion of an already gray image costs the same), each box blur variant (5 iterations), and 10 million calls of a managed `Add` method marked with `[MethodImpl(MethodImplOptions.NoInlining)]` vs 10 million calls of the native `imgf_add` (3 iterations). Use a helper method:

   ```csharp
   /// <summary>Returns the average time of one iteration in milliseconds.</summary>
   private static double Measure(string name, int iterations, Action action)
   {
       // Warm-up: JIT compilation, loading the native library, filling CPU caches
       action();

       var stopwatch = Stopwatch.StartNew();
       for (int i = 0; i < iterations; i++)
           action();
       stopwatch.Stop();
       // ...
   }
   ```

Run the program in the Release configuration – in Debug, the JIT does not optimize the code, so the measurements are meaningless (print a warning in `#if DEBUG`):

```bash
dotnet run -c Release
```

Example output (Linux x64, GCC 15 `-O2`; your times will differ):

```text
=== Managed filters ===
Grayscale same as native: safe True, Span True, unsafe True
Box blur: safe same as unsafe: True
=== Benchmark ===
Image: 1920x1080
Grayscale: safe (byte[])           2.79 ms
Grayscale: Span<Rgb24>             2.63 ms
Grayscale: unsafe (pointers)       1.93 ms
Grayscale: native (C)              2.18 ms
Box blur: safe (byte[])           39.05 ms
Box blur: unsafe (pointers)       27.88 ms
10M calls: managed Add            19.29 ms
10M calls: native imgf_add        23.83 ms
One call: managed 1.93 ns, native 2.38 ns
```

What do these numbers show?
- **Bounds checks.** In the safe convolution, each of the 9 reads from `src[...]` (and from `kernel[...]`) is preceded by a range check. The JIT removes such checks only when it can prove that the index is in range – typically in a loop `for (int i = 0; i < array.Length; i++)`. Indices such as `above + left + c` are checked every time, so the safe variant is about 40% slower than the one using pointers. In the simple grayscale conversion, the difference is much smaller.
- **Native code is not magic.** C# compiled by the JIT and C compiled by GCC can lead to very similar machine code – the unsafe C# variant is as fast as C. Calling native code pays off when the library already exists or uses something unavailable in .NET, not just to "make it faster". Bigger gains come from better algorithms and vectorization (`Vector128<T>`, `Vector<T>`).
- **The cost of a transition.** A P/Invoke call with blittable arguments costs only a few nanoseconds, similar to a regular method call – but such a method cannot be inlined, and every non-blittable argument (`string`, `bool[]`) adds conversion and copying. One call per image is negligible; one call per pixel (2 million calls) would take longer than the whole grayscale filter. Native APIs should therefore be *coarse-grained* – one call processes the whole buffer.

> [!TIP]
> `Stopwatch` with a warm-up is enough for a rough comparison. For reliable measurements (many runs, statistics, memory allocations), use the [BenchmarkDotNet](https://benchmarkdotnet.org/) library.

### Stage 5: Callbacks and Handles

So far, the memory has always belonged to C#. Now the library will allocate the image itself and return a pointer to an object whose layout is hidden from us (an *opaque type*), and the long-running convolution will report its progress by calling a C# function.

> [!IMPORTANT]
> #### `SafeHandle`
>
> A pointer to a native object could be stored as `nint`, but then we have to remember to release it – exactly once, also when an exception is thrown, and never while another thread is still using it. A class derived from `SafeHandle` solves these problems:
> - its `ReleaseHandle()` method is called exactly once – from `Dispose()` or, if we forget about it, from the finalizer,
> - when it is used as a parameter of a P/Invoke function, its reference count is increased for the duration of the call, so the handle cannot be released in the meantime,
> - it can be the return type of an imported function – the marshaller creates the object (using the **public** parameterless constructor, otherwise the build fails with `SYSLIB1051`) and stores the native pointer in it.
>
> `SafeHandleZeroOrMinusOneIsInvalid` is a base class for handles for which `0` (`NULL`) and `-1` mean an invalid value:
>
> ```csharp
> public sealed class SafeImageHandle : SafeHandleZeroOrMinusOneIsInvalid
> {
>     // Called by the marshaller when a native function returns imgf_image*
>     public SafeImageHandle() : base(ownsHandle: true)
>     {
>     }
>
>     protected override bool ReleaseHandle()
>     {
>         ImgFilterNative.ImageDestroy(handle);
>         return true;
>     }
> }
> ```

> [!IMPORTANT]
> #### Function Pointers and `[UnmanagedCallersOnly]`
>
> A C function pointer `void (*)(int32_t, int32_t)` corresponds in C# to an unmanaged function pointer `delegate* unmanaged[Cdecl]<int, int, void>` (the last type argument is the return type). It can point to a static method marked with `[UnmanagedCallersOnly]` – the JIT generates for it an entry point that can be called directly from native code. Such a method:
> - must be `static` and can have only blittable parameters and return type,
> - cannot be called from C# (error `CS8901`) – we only take its address with `&`,
> - **must not throw exceptions** – an exception cannot propagate through native code, so the process is terminated (a `try`/`catch` around the P/Invoke call does not help).
>
> ```csharp
> [UnmanagedCallersOnly(CallConvs = [typeof(CallConvCdecl)])]
> private static void ReportProgress(int doneRows, int totalRows) { /* ... */ }
>
> delegate* unmanaged[Cdecl]<int, int, void> progress = &ReportProgress;
> ```

1. In `imgfilter.h`, declare an opaque type (the fields of `struct imgf_image` are defined only in `imgfilter.c`), the callback type and the functions:

   ```c
   typedef struct imgf_image imgf_image;

   /* Called after each processed row */
   typedef void (*imgf_progress_fn)(int32_t done_rows, int32_t total_rows);

   IMGF_API imgf_image* imgf_image_create(int32_t width, int32_t height, int32_t channels);
   IMGF_API void imgf_image_destroy(imgf_image* image);
   IMGF_API imgf_info imgf_image_info(const imgf_image* image);
   IMGF_API uint8_t* imgf_image_pixels(imgf_image* image);
   IMGF_API int32_t imgf_image_convolve3x3(imgf_image* image, const int32_t kernel[9], int32_t divisor,
                                           imgf_progress_fn progress);
   /* Number of images created and not yet destroyed */
   IMGF_API int32_t imgf_live_images(void);
   ```

2. Implement them in `imgfilter.c`. `struct imgf_image` contains an `imgf_info` and a pointer to the pixels. `imgf_image_create` returns `NULL` for invalid arguments or when memory cannot be allocated, and increments a `static` counter of living images (`imgf_image_destroy` decrements it). `imgf_image_info` returns the struct **by value**. `imgf_image_convolve3x3` implements the same algorithm as `Convolve3x3Safe` in place: it first copies the pixels to a temporary buffer (every output pixel needs the original neighbours), and after every row calls `progress(y + 1, height)`, if `progress` is not `NULL`.
3. In C#, create `SafeImageHandle` (`Interop/SafeImageHandle.cs`, as above) and declare the new functions in `ImgFilterNative`. The class now needs the `unsafe` modifier, because some declarations use pointers:

   ```csharp
   [LibraryImport(Lib, EntryPoint = "imgf_image_create")]
   internal static partial SafeImageHandle ImageCreate(int width, int height, int channels);

   // Called only from SafeImageHandle.ReleaseHandle, hence the raw handle
   [LibraryImport(Lib, EntryPoint = "imgf_image_destroy")]
   internal static partial void ImageDestroy(nint image);

   [LibraryImport(Lib, EntryPoint = "imgf_image_pixels")]
   internal static partial byte* ImageGetPixels(SafeImageHandle image);

   [LibraryImport(Lib, EntryPoint = "imgf_image_convolve3x3")]
   internal static partial int ImageConvolve3x3(SafeImageHandle image, ReadOnlySpan<int> kernel, int divisor,
       delegate* unmanaged[Cdecl]<int, int, void> progress);
   ```

   Also declare `ImageGetInfo` (returning `ImageInfo`) and `LiveImages`, and add the property `ImgFilter.LiveImages`.
4. Create a class `public sealed unsafe class NativeImage : IDisposable` (`NativeImage.cs`), which wraps a `SafeImageHandle`:
   - The constructor `(int width, int height, int channels)` creates the native image and throws an `ArgumentException` if the handle `IsInvalid`. It stores the `ImageInfo` returned by `ImageGetInfo` in the `Info` property.
   - The `Pixels` property returns `new Span<byte>(pointer, length)` – a span over native memory, without copying. Throw an `ObjectDisposedException` when the handle is already closed (`ObjectDisposedException.ThrowIf(_handle.IsClosed, this)`).
   - `static NativeImage FromImage(Image image)` and `Image ToImage()` copy the pixels between managed and native memory (`Span<T>.CopyTo`).
   - `Convolve3x3(ReadOnlySpan<int> kernel, int divisor, bool reportProgress = false)` calls the native convolution, passing `&ReportProgress` or `null`. `ReportProgress` prints a line every 25% of rows: `int step = Math.Max(1, totalRows / 4);` and prints when `doneRows % step == 0 || doneRows == totalRows`.
   - `Dispose()` disposes the handle.
5. In `Program.cs`, add `RunNativeImage(Image input)`, which:
   - in a `using` block, creates a `NativeImage` from the input, prints its `Info` and the number of living native images, blurs it with progress reporting (the kernel can be given as a collection expression `[1, 1, 1, 1, 1, 1, 1, 1, 1]` – for a `ReadOnlySpan<int>` parameter, the compiler does not allocate an array) and compares the result with `ManagedFilters.BoxBlur`; then copies the input image into it again, sharpens it with the kernel `[0, -1, 0, -1, 5, -1, 0, -1, 0]` and divisor `1`, and saves the result to `sharpen.ppm`;
   - after the `using` block, prints the number of living images again;
   - calls a helper `CreateAndForget()` (marked with `[MethodImpl(MethodImplOptions.NoInlining)]`), which creates a `NativeImage` and does not dispose it, prints the number of living images, calls `GC.Collect()` and `GC.WaitForPendingFinalizers()`, and prints it once more – the `SafeHandle` finalizer releases the forgotten image.
6. In `Benchmark`, also measure the native box blur.

> [!WARNING]
> A `Span<byte>` over native memory is not tracked by the GC – after `Dispose()`, a span obtained earlier points to freed memory (*use after free*), just like a dangling pointer in C++. Keep such spans short-lived, and copy the data (`ToImage()`) if you need it longer. An alternative without `unsafe` code is `Marshal.Copy(nint source, byte[] destination, int startIndex, int length)`.

> [!TIP]
> Instead of a function pointer, you can also pass a delegate. It can be an instance method or a lambda capturing local variables, which `[UnmanagedCallersOnly]` does not allow. `Marshal.GetFunctionPointerForDelegate` creates a native entry point for it – but it remains valid only as long as the delegate object is alive. The GC does not see references held by native code, so the delegate must be kept alive until the native code stops using the pointer (`GC.KeepAlive`, or a field if the native code stores the pointer for later):
>
> ```csharp
> [UnmanagedFunctionPointer(CallingConvention.Cdecl)]
> delegate void ProgressCallback(int doneRows, int totalRows);
>
> var callback = new ProgressCallback((done, total) => Console.WriteLine($"{done}/{total}"));
> nint pointer = Marshal.GetFunctionPointerForDelegate(callback);
> ImgFilterNative.ImageConvolve3x3(handle, kernel, 9, (delegate* unmanaged[Cdecl]<int, int, void>)pointer);
> GC.KeepAlive(callback); // the delegate must not be collected before this line
> ```

### Next Steps and Further Enhancements

The application built in this tutorial can be extended in many directions:

- **Vectorization (SIMD):** Implement the filters with `Vector128<T>`/`Vector256<T>` or `System.Numerics.Tensors.TensorPrimitives`, and compare them with C compiled with `-O3 -march=native`. Vectorization usually gives a much bigger speedup than switching to C.
- **Parallelism:** Process rows in parallel with `Parallel.For` in C# (or with OpenMP in C). Note that the progress callback would then be called from many threads at the same time.
- **Callback context:** Real C libraries pass an additional `void* user_data` argument to callbacks. Pass a `GCHandle` of a managed object (`GCHandle.ToIntPtr`) through it, to route the callback to an instance method or an `IProgress<T>`.
- **Custom marshalling:** Structs containing strings or `bool` are not blittable. Define how to convert them with the `[NativeMarshalling]` and `[CustomMarshaller]` attributes.
- **Cross-platform build:** Replace the compiler commands in the `.csproj` file with CMake, and package the library for several systems in a NuGet package (`runtimes/<rid>/native/`).
- **A C++ library:** Rewrite `imgfilter` in C++. Remember about `extern "C"` and that C++ exceptions must not propagate out of exported functions.
